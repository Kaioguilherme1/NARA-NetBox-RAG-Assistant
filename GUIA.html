NARA, por dentro

O NARA é um assistente interno para NetBox baseado em DeepAgent + RAG em pgvector. Ele consulta documentação institucional, responde com evidência documentada e oferece uma API compatível com OpenAI consumida por uma UI web. Este guia descreve a arquitetura, o fluxo de ingestão e os pontos de extensão do projeto.

Antes de tudo: colocar no ar

Ler o código com ele rodando ao lado vale o dobro. São dois comandos e um arquivo de configuração.

Configure suas credenciais

Na pasta app/, copie o exemplo e preencha a chave e o endpoint:

cd app
cp .env.example .env

As duas variáveis que importam são OPENAI_API_KEY e OPENAI_BASE_URL. O projeto usa Azure AI Foundry, cujo endpoint termina em /openai/v1/ e fala o protocolo da OpenAI — por isso nenhuma linha de código muda para trocar de provedor.

Suba o backend

docker compose up --build -d

Isso levanta dois containers: o Postgres com a extensão pgvector e o agent-api. Na primeira subida, o app lê os PDFs de app/documentos/, corta em pedaços, gera os embeddings e grava no banco.

O sinal de que deu certo aparece no log:

docker compose logs agent-api

agent-api-1  | Ingeridos 180 chunks de 3 documento(s).
agent-api-1  | INFO:     Uvicorn running on http://0.0.0.0:8000

E o teste rápido:

curl http://localhost:18080/v1/models
{"object":"list","data":[{"id":"nara",...}]}

Suba a interface

cd ../ui
npm install
npm run dev

Abra o endereço que o Next.js imprimir no terminal — normalmente http://localhost:3000, mas ele troca de porta sozinho se ela estiver ocupada, então confie no log e não no que você espera.

A UI descobre o backend pelo arquivo ui/.env.local:

AGENT_API_URL=http://localhost:18080/v1
AGENT_API_KEY=sk-local-nao-usado
A porta engana

O README.md e o frontend/.env.local.example dizem que o backend fica em localhost:8000. O docker-compose.yml publica 18080 no seu computador (mapeado para a 8000 dentro do container). Se o chat não responder, é quase sempre isto: confira o AGENT_API_URL.

Prefere não instalar Node? Existe um atalho: python app.py sobe uma interface Gradio em :7860 usando exatamente o mesmo agente. Veja a seção do Gradio.

Ao percorrer o código daqui em diante, preste atenção especial em como a tool_rag é declarada (é o molde da sua segunda tool) e em como o agente é montado no fim do agent_core.py (é onde o subagente entra). O resto você aproveita quase inteiro.

A ideia central

Se você guardar uma só frase deste guia, guarde esta: o agente se disfarça de OpenAI.

O server.py implementa dois endpoints que a API da OpenAI tem — GET /v1/models e POST /v1/chat/completions. Do lado de fora, qualquer cliente compatível com OpenAI acha que está conversando com um modelo chamado nara. Do lado de dentro, o DeepAgent decide quando buscar na base documental do NetBox.

Essa escolha é o que dá liberdade ao projeto: a mesma API serve o assistant-ui, o Open WebUI, o LibreChat, um script com curl ou um notebook. Trocar a interface não toca em uma linha do agente.

O repositório tem três entradas para o mesmo núcleo: a API (server.py), uma UI Gradio (app.py) e o notebook do curso. Todas importam agent_core.py. É esse o padrão que vale copiar no seu projeto.

agent_core.py, o núcleo

186 linhas que fazem tudo o que importa: configuração, ingestão, busca e montagem do agente. Entendendo este arquivo, você entendeu o projeto.

Configuração

linhas 20–36

Tudo que muda entre ambientes vem de variável de ambiente, com default para rodar local:

load_dotenv()
DB_URI       = os.environ.get("DB_URI", "postgresql://...@localhost:5432/rag")

Repare que a chave da Azure não aparece no código: OPENAI_API_KEY e OPENAI_BASE_URL são lidas pelo próprio cliente da LangChain, direto do ambiente. É por isso que apontar para o Foundry em vez da OpenAI não exigiu mudança nenhuma de código — só de .env.

SYSTEM_PROMPT

linhas 26–34

O prompt é curto, mas cada frase faz um trabalho. Leia devagar e identifique as cinco partes:

  • Papel — "Você é NARA, assistente interno especializado em NetBox, técnico e objetivo."
  • Gatilho da ferramenta — "Para QUALQUER pergunta sobre cartões, benefícios, seguro, cobertura ou assistência, SEMPRE chame a tool_rag ANTES de responder." Note o vocabulário: são as palavras que o usuário usaria, não o nome interno do documento.
  • Ancoragem — "baseie-se apenas nos trechos retornados".
  • Citação — o formato [Fonte: ...] chega dentro do texto da ferramenta, e o prompt manda listar as fontes no fim.
  • Saída honesta — "se não estiver nos trechos, diga que não encontrou". É esta linha que produz o "não encontrei na base" em vez de invenção.
Por que isso importa

O prompt não descreve o que a ferramenta faz — quem descreve é a docstring dela. O prompt só diz quando usar e como se comportar com o resultado. Essa divisão de responsabilidade é o que evita prompt gigante, e é o erro mais comum de quem escreve a primeira ferramenta.

conectar() e pg()

linhas 39–57

Uma conexão global, criada sob demanda, com até 15 tentativas espaçadas de 3s — ou seja, 45 segundos de tolerância esperando o Postgres subir. Isso existe porque no docker compose e no Kubernetes o banco e o app sobem juntos, e o app quase sempre ganha a corrida.

depends_on no compose garante ordem de início, não que o Postgres esteja pronto para aceitar conexão. O retry cobre essa diferença — um detalhe que você vai querer copiar em qualquer app que suba junto com seu banco.

preparar_base()

linhas 60–97 ingestão

É o pipeline de RAG inteiro, em 35 linhas:

# 1. extensão e tabela
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE IF NOT EXISTS chunks (
  id bigserial PRIMARY KEY, content text, source text, embedding vector(1536)
);

# 2. guarda de idempotência
SELECT count(*) FROM chunks;   → se > 0, retorna sem fazer nada

# 3. PDF → texto → chunks → vetores → INSERT
pymupdf.open(caminho)                         # texto de cada página
RecursiveCharacterTextSplitter(1000, 100)     # ~1000 chars, 100 de sobreposição
emb.embed_documents(pedacos)                  # 1 chamada por arquivo, em lote

A coluna source guarda o nome do arquivo sem extensão, e é ela que vira o [Fonte: ...] na resposta. A sobreposição de 100 caracteres existe para que uma frase cortada no fim de um chunk reapareça inteira no começo do próximo.

Isto vai te pegar

A guarda de idempotência é count(*) > 0, não uma comparação de conteúdo. Trocar os PDFs e reiniciar não reingere nada — a base velha continua lá e o agente segue respondendo sobre os documentos antigos. Para trocar o corpus é preciso apagar o volume: docker compose down -v.

tool_rag()

linhas 100–154 a ferramenta

Aqui mora a parte mais importante para quem vai criar o próprio agente. Comece pela docstring, porque ela não é comentário — é interface:

def tool_rag(pergunta: str) -> str:
    """Busca trechos na documentação do NetBox e padrões internos (pgvector)
    para fundamentar a resposta. Use para perguntas sobre modelagem, operação,
    Device Types, interfaces e documentação institucional. Cada trecho vem
    marcado com [Fonte: ...] para você citar."""

A LangChain converte a assinatura e a docstring no schema JSON que vai para o modelo. O nome do parâmetro, o type hint e esse texto são tudo o que o LLM sabe sobre a ferramenta na hora de decidir chamá-la. Docstring vaga produz agente que não busca — ou que busca sempre.

A busca em si tem duas pernas e um filtro:

EtapaO que fazSQL
Filtro por cartão Se a pergunta cita platinum/gold/standard, restringe ao documento certo source ILIKE '%platinum%'
Perna 1 — semântica Os 5 chunks mais próximos do vetor da pergunta ORDER BY embedding <=> %s LIMIT 5
Perna 2 — lexical Até 4 chunks que contenham as palavras da pergunta, ordenados por proximidade vetorial WHERE content ILIKE ... LIMIT 4
Fusão Dicionário por id — a perna semântica tem prioridade, a lexical só acrescenta o que faltou resultados.setdefault(...)
Corte No máximo 7 trechos, cada um prefixado com sua fonte list(...)[:7]

O operador <=> do pgvector é distância de cosseno: quanto menor, mais parecido. Por isso o ORDER BY é crescente, sem DESC.

A perna lexical filtra palavras com 5 letras ou mais e descarta uma lista de stopwords do domínio (qual, cartao, seguro, cobertura…). A ideia é sobrar só o termo raro — "bagagem", "extravio", "franquia" — que é justamente onde a busca vetorial às vezes escorrega.

Isso é busca híbrida?

É a versão didática dela. Busca híbrida de produção usa BM25 (ou ts_vector) para a perna lexical e funde os dois rankings com RRF, ponderando posições. Aqui a perna lexical é um ILIKE e a fusão é "quem chegou primeiro fica". Funciona bem no tamanho desta base e é legível numa leitura; não é o que você levaria para produção com milhões de chunks.

construir_agente()

linhas 157–185 montagem

Uma função, dois modos. Com persistente=True (usado pelo Gradio):

store       = PostgresStore(conectar());  store.setup()
checkpointer = PostgresSaver(conectar()); checkpointer.setup()

create_deep_agent(
    model=ChatOpenAI(model=MODELO_CHAT, temperature=0),
    tools=[tool_rag],
    system_prompt=SYSTEM_PROMPT,
    backend=CompositeBackend(
        default=StateBackend(),
        routes={"/memories/": StoreBackend(namespace=lambda ctx: ("memories",))},
    ),
    store=store, checkpointer=checkpointer,
)

O CompositeBackend é o filesystem virtual do agente, com um roteador de caminhos: qualquer arquivo que o agente escrever em /memories/ vai para o Postgres e sobrevive ao restart; o resto vive no StateBackend e some no fim da conversa. É memória de longo prazo com granularidade de pasta.

Com persistente=False (usado pelo server.py), é uma linha só: create_deep_agent(model, tools, system_prompt). Sem store, sem checkpointer, sem rota de memória — tudo efêmero.

O que o create_deep_agent te dá de graça

O código declara uma ferramenta. O agente roda com dez.

Isso não está escrito em lugar nenhum do projeto — só aparece se você inspecionar o grafo compilado. Vale fazer você mesmo, com o backend rodando:

>>> list(agente.nodes)
['__start__', 'model', 'tools', 'PatchToolCallsMiddleware.before_agent']

>>> sorted(agente.nodes['tools'].bound.tools_by_name)
['delete', 'edit_file', 'execute', 'glob', 'grep', 'ls',
 'read_file', 'task', 'tool_rag', 'write_file']

Nove ferramentas vêm do harness do DeepAgents e uma é sua. Elas se dividem em dois grupos:

GrupoFerramentasPara que serve
Filesystem virtual ls read_file write_file edit_file glob grep delete Rascunho do agente. Ele guarda resultados intermediários em "arquivos" em vez de carregar tudo no contexto. É onde entra a rota /memories/.
Orquestração task execute task delega a um subagente com contexto isolado. É o mecanismo por trás de subagents=[...].
"Então esse agente pode apagar arquivos?"

Pode — mas do filesystem virtual, que neste modo vive só na memória da conversa. Não é o disco do container nem o seu computador. Vale saber disso antes de se assustar com a lista de ferramentas na primeira vez que ela aparecer num log.

A assinatura completa da função mostra por onde o projeto pode crescer sem trocar de framework:

create_deep_agent(
    model, tools, *, system_prompt, middleware=(), subagents=None,
    skills=None, memory=None, permissions=None, backend=None,
    interrupt_on=None,      # human-in-the-loop: pausa antes de X
    response_format=None,   # saída estruturada (Pydantic)
    state_schema=None, context_schema=None,
    checkpointer=None, store=None, name=None, cache=None,
)

Os quatro que mais vão te interessar: subagents (dividir trabalho), interrupt_on (aprovação humana antes de uma ação destrutiva), permissions (restringir o filesystem) e response_format (resposta em JSON validado).

server.py, o disfarce

83 linhas que traduzem o agente para o protocolo da OpenAI.

Três detalhes que merecem atenção:

O agente é construído no import

agente = construir_agente(persistente=False)   # nível de módulo

Roda uma vez, no boot do processo — e como construir_agente chama preparar_base(), a ingestão acontece na subida do container, não na primeira pergunta. Bom: a primeira resposta não paga o custo. Ruim: se a ingestão falhar, o container não sobe. É por isso que a linha Ingeridos 180 chunks aparece no log antes de qualquer requisição.

O histórico é peneirado

def _historico(req_messages):
    """Mantem apenas role + content textual (ignora conteudo multimodal)."""

Só passam mensagens cujo content é string e cujo papel é system/user/assistant. Isso descarta silenciosamente anexos, imagens e blocos de conteúdo estruturado. Se você anexar um PDF na UI e nada acontecer, a explicação está nesta função.

O SSE é montado à mão

for token, _meta in agente.stream(mensagens, cfg, stream_mode="messages"):
    if isinstance(token, AIMessageChunk) and token.content:
        yield "data: " + json.dumps(pedaco) + "\n\n"
...
yield "data: [DONE]\n\n"

stream_mode="messages" entrega os tokens do LLM conforme saem. O isinstance(token, AIMessageChunk) filtra o que não é texto do assistente. Cada token vira um chunk no formato da OpenAI, e o [DONE] fecha o stream — é a convenção que todo cliente OpenAI espera.

Guarde para depois

Esse filtro captura tokens de qualquer nó do grafo. Num agente com subagentes, o "pensamento" deles apareceria no stream do usuário. Aqui não acontece porque não há subagentes — mas é a primeira coisa a checar quando você adicionar subagents=[...] e o chat começar a mostrar texto estranho.

O caminho de uma pergunta

"Quanto o Platinum cobre de bagagem?" — o que acontece, em ordem.

Repare no que não existe: não há if "cartao" in pergunta em lugar nenhum. Quem decide chamar a ferramenta é o modelo, com base na docstring e no system prompt. É a diferença entre um chatbot com regras e um agente.

Custo escondido

Toda chamada de tool_rag gera um embed_query — uma ida à API de embeddings antes de qualquer SQL. Nesse tipo de pipeline, o embedding da pergunta costuma dominar a latência da busca com folga sobre o tempo de banco. Se um dia você for otimizar, olhe para cache/warmup do embedding antes de mexer no SQL.

As três memórias

"O agente lembra de mim?" depende de qual memória e de qual entrada. Esta tabela resolve a maior parte da confusão.

CamadaOnde moraDuraAtiva no server.py?
Histórico da conversa No cliente — a UI reenvia tudo a cada requisição Enquanto a aba viver Sim — é a única ativa
Checkpointer
PostgresSaver		 Postgres, indexado por thread_id Permanente, por conversa Não — só com persistente=True
Store
PostgresStore		 Postgres, namespace memories Permanente, atravessa conversas Não — só com persistente=True

Por isso o server.py gera um thread_id novo a cada requisição: sem checkpointer, o id não guarda nada mesmo — é só um campo obrigatório da config. O comentário no topo do arquivo diz isso com todas as letras: "a UI manda o historico completo a cada requisicao, entao o backend e stateless".

Teste você mesmo: pergunte sobre o Platinum e em seguida só "e no Gold?". Funciona, porque o histórico veio junto na requisição. Agora recarregue a página e repita a segunda pergunta sozinha — o agente não faz ideia do que você está falando.

Como ligar memória de verdade

O próprio README aponta o caminho: derive o thread_id da sessão do usuário em vez de sortear um uuid, e construa o agente com persistente=True. A partir daí o checkpointer assume e o histórico deixa de depender do cliente.

app.py, o atalho

A mesma inteligência, sem Node, em 38 linhas.

Usa gr.ChatInterface com uma função geradora que acumula os tokens e faz yield do texto parcial — é assim que o Gradio desenha o streaming. E constrói o agente com persistente=True, então esta entrada tem checkpointer e store.

É o caminho mais rápido para ver o agente funcionando: python app.py e abra :7860. Também é o que o notebook usa no Colab, com share=True para gerar um link público.

Não use como está para vários usuários

O thread_id é a string fixa "web". Todo mundo que abrir a mesma instância cai na mesma thread, com o mesmo histórico e a mesma memória de longo prazo. Sozinho na sua máquina, tudo bem; num link compartilhado, uma pessoa vê a conversa da outra.

A UI: um starter e um arquivo seu

São ~4.150 linhas de componentes em ui/, e você não precisa entender quase nenhuma.

A pasta veio de npx assistant-ui@latest create, praticamente intocada — o <title> ainda é "assistant-ui Starter App". A pilha: Next.js 16 (App Router, Turbopack), React 19, Tailwind 4, componentes shadcn/ui sobre @base-ui/react, e o Vercel AI SDK v7 fazendo a ponte.

O único arquivo realmente do projeto é ui/app/api/chat/route.ts, e ele cabe em meia tela:

const agente = createOpenAI({
  baseURL: process.env.AGENT_API_URL ?? "http://localhost:18080/v1",
  apiKey:  process.env.AGENT_API_KEY ?? "sk-local-nao-usado",
});

const result = streamText({
  model: agente.chat("nara"),
  messages: await convertToModelMessages(messages),
});

É o cliente oficial da OpenAI apontado para outro baseURL. A chave é decorativa — o backend não valida nada. E .chat(...) é deliberado: força o AI SDK a usar /v1/chat/completions em vez da Responses API, que o server.py não implementa.

Por que essa rota existe?

Ela roda no servidor do Next, não no navegador. Assim a URL e a credencial do backend nunca chegam ao cliente — e em produção o AGENT_API_URL pode apontar para um endereço interno do cluster (http://agent-api:8000/v1), inalcançável de fora. É o que o k8s/frontend.yaml faz.

Existe uma segunda versão desse arquivo em app/frontend/route.ts, que é a de referência do curso. Ela usa a API mais antiga do SDK (createUIMessageStreamResponse) e aponta para a porta 8000. A que roda é a de ui/.

Infra e CI/CD

Docker

O Dockerfile é o mínimo: python:3.12-slim, instala o requirements.txt, copia o código, roda uvicorn. Sem multi-stage e sem usuário não-root — didático, mas não é o que se leva para produção.

No docker-compose.yml há duas decisões que valem entender:

  • O Postgres não publica porta no host. O agent-api chega nele pela rede interna, como db:5432. Menos superfície exposta.
  • A pasta ./documentos é montada como volume, então dá para trocar os PDFs sem rebuildar a imagem — desde que você limpe a base, pelo motivo da idempotência.

Kubernetes

Cinco manifests, e dois detalhes que ensinam algo:

  • O readinessProbe bate em /v1/models com initialDelaySeconds: 30 — margem para a ingestão que roda no boot.
  • O Ingress tem proxy-read-timeout: 3600. Streaming é uma conexão longa; com o timeout padrão do nginx a resposta seria cortada no meio. É a pegadinha clássica de colocar chat com SSE atrás de proxy.

GitHub Actions

ci.yml compila os três arquivos Python, roda ruff e builda a imagem. deploy.yml dispara em tags v*: publica no GHCR, aplica os manifests e faz kubectl set image + rollout status.

O lint não reprova

A linha é ruff check . || true. O || true engole a falha: o job fica verde mesmo com o código sujo. Se você usar esse CI como base, é a primeira linha a corrigir.

O notebook, e onde ele difere

28 células em três partes: rodar no Colab, empacotar o app, hospedar.

A Parte B usa %%writefile para gerar os arquivos do projeto — é como a pasta app/ nasce. Por isso o notebook e o repositório são duas versões da mesma coisa, e há diferenças reais entre o protótipo da Parte A e o app final:

AspectoNotebook (Parte A)App (agent_core.py)
TabelaDROP TABLE e recria sempreCREATE IF NOT EXISTS, pula se populada
Índice vetorialCria índice HNSWNenhum índice
Coluna sourceNão existeExiste, alimenta as citações
BuscaSó vetorial, LIMIT 3Vetorial + lexical, até 7
Todos os PDFsConcatenados num texto sóUm por vez, preservando a fonte

A diferença do índice merece atenção. Sem índice, o pgvector faz varredura sequencial e calcula distância contra todos os chunks. Com 180 chunks isso é imperceptível. A partir de dezenas de milhares, passa a doer — e aí o CREATE INDEX ... USING hnsw que está no notebook precisa voltar para o app.

Do exemplo ao seu projeto

A ordem importa. Cada passo é testável antes do próximo — e os passos 6 e 7 são os dois requisitos que este exemplo não cobre.

  1. Troque os documentos. Seus arquivos em app/documentos/. Como a base não reingere sozinha, derrube o volume: docker compose down -v e suba de novo.
  2. Reescreva o SYSTEM_PROMPT. Papel, quando chamar a ferramenta (no vocabulário de quem vai perguntar), ancoragem nos trechos, formato da citação e o que fazer quando não souber. As cinco partes.
  3. Ajuste a docstring da tool_rag. É o que o modelo lê para decidir. Descreva o seu corpus.
  4. Revise o filtro por fonte. O bloco ["platinum", "gold", "standard"] é específico deste domínio. Se o seu corpus não se divide assim, apague — ou troque pelas categorias reais.
  5. Confira as stopwords da perna lexical: cartao, seguro, cobertura são as palavras genéricas deste domínio. As suas serão outras.
  6. Escreva a segunda tool — obrigatória na entrega. Veja abaixo.
  7. Declare um subagente — obrigatório na entrega. Veja abaixo.
  8. Renomeie o modelo em MODEL_ID (server.py) e no agente.chat("...") do route.ts — os dois têm que combinar, senão a UI pede um modelo que não existe.

Passo 6 — a segunda tool

Uma tool é uma função Python comum. O que a torna utilizável pelo agente são três coisas: type hints nos parâmetros, docstring descritiva e a inclusão em tools=[...]. Não há decorator obrigatório nem registro em lugar nenhum.

Um exemplo que funciona com o schema deste projeto — o agente passa a saber responder "o que você pode consultar?":

def listar_documentos() -> str:
    """Lista os documentos disponiveis na base de conhecimento e quantos
    trechos cada um tem. Use quando o usuario perguntar sobre o que voce
    pode responder, ou quais fontes voce consulta."""
    cur = pg().cursor()
    cur.execute("SELECT source, count(*) FROM chunks GROUP BY source ORDER BY source")
    linhas = [f"- {fonte}: {n} trechos" for fonte, n in cur.fetchall()]
    return "\n".join(linhas) if linhas else "A base esta vazia."

E o registro, no construir_agente():

create_deep_agent(
    model=modelo,
    tools=[tool_rag, listar_documentos],   # ← as duas
    system_prompt=SYSTEM_PROMPT,
)

Escolha a sua segunda tool pelo que ela resolve, não pelo que é fácil: uma que consulte uma API externa, calcule algo que o modelo erraria sozinho, ou consulte metadados da base como esta. Uma tool que só reformata texto é trabalho que o LLM já faz.

Passo 7 — o subagente

Um subagente é declarado como um dicionário. Três campos são obrigatórios — name, description e system_prompt — e tools é opcional (se você omitir, ele herda as do agente principal):

pesquisador = {
    "name": "pesquisador",
    "description": (
        "Investiga um tema a fundo na base, cruzando varios documentos. "
        "Use quando a pergunta exigir comparar fontes ou reunir informacao "
        "espalhada, em vez de uma consulta pontual."
    ),
    "system_prompt": (
        "Voce pesquisa na base de conhecimento. Faca quantas buscas forem "
        "necessarias com a tool_rag, uma por subtema. Devolva um resumo "
        "objetivo, sempre citando as fontes de cada afirmacao."
    ),
    "tools": [tool_rag],
}

create_deep_agent(
    model=modelo,
    tools=[tool_rag, listar_documentos],
    system_prompt=SYSTEM_PROMPT,
    subagents=[pesquisador],               # ← delegação hierárquica
)

O agente principal aciona o subagente pela ferramenta task, que — como você viu na seção das dez ferramentas — já estava disponível o tempo todo. Quem decide delegar é o modelo, lendo a description. É o mesmo mecanismo da tool_rag: a descrição é a interface.

Por que isso vale a pena, e não é só requisito: o subagente roda com contexto isolado. Ele pode fazer seis buscas, ler trechos longos e descartar o que não serve, devolvendo só o resumo ao agente principal. O contexto do chat não incha com o material bruto da pesquisa.

Efeito colateral que você vai ver

Assim que houver subagente, o server.py passa a transmitir também os tokens dele — o filtro do streaming captura qualquer AIMessageChunk do grafo, venha de onde vier. Na prática, o raciocínio interno do subagente pode aparecer no chat. Se acontecer, não é bug do seu subagente: é o filtro em server.py que precisa distinguir a origem do token.

Sobre o README da entrega

Três coisas são pedidas explicitamente, e as duas últimas são as que costumam ficar para a última hora:

  • Setup — .env, docker compose up, como rodar. A primeira seção deste guia serve de modelo; confira a porta que o seu compose publica.
  • 3 perguntas-teste com resposta esperada — escolha perguntas que exercitem caminhos diferentes: uma que force o RAG, uma que o agente deva responder sem buscar, e uma cuja resposta correta seja "não encontrei na base". Um trio que só testa o caminho feliz não mostra nada.
  • Caso de uso e limitações conhecidas — o que o agente resolve, para quem, e onde ele falha. Seja específico: "não compara dois documentos na mesma pergunta" vale mais que "pode conter imprecisões".
O passo que quebra silenciosamente

Se você trocar MODELO_EMBED por text-embedding-3-large, os vetores passam a ter 3072 dimensões e a tabela está declarada como vector(1536), com o número escrito à mão no SQL. O erro aparece só na ingestão, e não é óbvio. Trocar o modelo de embedding exige mudar o CREATE TABLE e reingerir tudo.

Perguntas frequentes

Onde está o loop do agente? Não vejo while nenhum.

Não existe no código do projeto. O create_deep_agent devolve um grafo LangGraph compilado com dois nós principais, model e tools, e a aresta condicional entre eles: o modelo responde ou pede uma ferramenta; se pedir, o grafo executa e volta ao modelo. O loop é o grafo.

Como o modelo sabe que deve chamar a tool_rag?

Por duas vias que se somam. A LangChain converte a assinatura e a docstring da função num schema de ferramenta enviado ao modelo em toda requisição — é o canal principal. E o system prompt reforça com uma regra explícita ("SEMPRE chame antes de responder"). Sem a docstring, o modelo teria só o nome da função para adivinhar.

Qual a diferença entre isso e o create_agent da LangChain?

O DeepAgents é uma camada acima. Ele monta o mesmo tipo de grafo, mas já embute o harness: filesystem virtual (7 ferramentas), delegação a subagentes (task), planejamento, e ganchos para skills, memória e permissões. Com create_agent você teria a sua ferramenta e mais nada — o que às vezes é exatamente o que se quer.

Por que não usar langgraph dev ou a LangGraph Platform?

Porque aí a UI precisaria falar o protocolo da LangGraph. Expondo o formato da OpenAI, qualquer cliente pronto conecta sem adaptador — e a interface vira uma decisão descartável. Esse é o argumento central do projeto.

Dá para trocar o pgvector por outro banco vetorial?

Sim, e o impacto é pequeno: preparar_base() e tool_rag() mudam, o resto fica igual. A ferramenta é uma função que recebe uma string e devolve uma string — o agente não sabe o que tem atrás dela.

Como faço aprovação humana antes de uma ação perigosa?

Parâmetro interrupt_on do create_deep_agent. Ele pausa a execução antes das ferramentas que você listar e devolve o controle a quem chamou. Como este projeto só tem uma ferramenta de leitura, não há uso aqui — mas é o gancho certo para quando o seu agente escrever em algum lugar.

E multi-agente?

Parâmetro subagents=[...], com o formato completo no passo 7 da receita — é requisito da entrega. Cada subagente roda com contexto isolado e é acionado pela ferramenta task, que já está disponível.

Quanto custa cada pergunta?

Uma chamada de embedding por invocação da tool_rag (barata) mais a geração do modelo (o grosso). A ingestão é paga uma vez: a base documental é indexada no PostgreSQL. Perguntas sobre NetBox que não acionam a ferramenta não geram embedding nenhum.

Por que temperature=0?

Para RAG interessa reprodutibilidade e fidelidade ao trecho recuperado, não variedade. Com temperatura 0 a mesma pergunta tende a produzir a mesma resposta, o que também torna o comportamento avaliável — dá para rodar um conjunto de perguntas de referência e comparar.

A API tem autenticação?

Não. O server.py aceita qualquer requisição; a apiKey do route.ts é ignorada. Rodando local, tudo bem. Exposto na rede, não — qualquer um que alcance a porta gasta a sua chave do Foundry. Antes de publicar: autenticação, rate limiting e HTTPS.

Por que o agente às vezes responde sem citar fontes?

Porque não chamou a ferramenta — e nem sempre deveria. "Monte um roteiro de 5 dias em Lisboa" é conhecimento geral do modelo. A seção Fontes só aparece quando houve busca, que é o comportamento pedido pelo prompt.

Como sei se ele buscou mesmo, ou está inventando?

Três sinais, do mais fraco ao mais forte: a seção Fontes no fim da resposta; o log do container (docker compose logs -f agent-api); e — o definitivo — instrumentar com tracing (Langfuse) para ver a chamada de ferramenta, os argumentos e o texto recuperado. Este projeto ainda não tem tracing: é uma boa primeira extensão para você implementar.

O que costuma quebrar

Pontos frágeis reais do código. Ler esta lista antes economiza uma tarde de depuração.

no seu dia 1

O README aponta para a porta errada

O README e o frontend/.env.local.example dizem que o backend fica em localhost:8000. O docker-compose.yml publica 18080:8000. Quem segue a documentação configura 8000 e não conecta.

→ o valor correto é o que está em ui/.env.local: AGENT_API_URL=http://localhost:18080/v1

no seu dia 1

Trocar os PDFs não muda as respostas

A ingestão só roda com a tabela vazia. Novos documentos na pasta são ignorados enquanto houver qualquer chunk antigo — e o agente continua respondendo com segurança total sobre o corpus errado.

→ docker compose down -v antes de subir com o corpus novo

no seu dia 1

Comparação entre dois cartões sai enviesada

O filtro de fonte percorre ["platinum", "gold", "standard"] e para no primeiro que aparecer na pergunta. "Qual a diferença entre Gold e Platinum?" fixa em Platinum e busca só nesse documento — a comparação nasce sem metade dos dados.

→ pergunte um cartão por vez, ou reescreva o filtro para coletar todas as fontes citadas

antes de produção

Sem índice vetorial

A tabela não tem índice; toda busca é varredura sequencial. Invisível com 180 chunks, custoso em escala. O notebook do curso cria HNSW — o app perdeu isso no caminho.

→ CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

antes de produção

Dimensão 1536 escrita à mão

O CREATE TABLE fixa vector(1536), casado com o text-embedding-3-small. Trocar o modelo de embedding por variável de ambiente não atualiza o schema.

→ derive a dimensão do modelo, ou trate os dois como um par que muda junto

antes de produção

Sem autenticação, e com senha padrão no banco

A API aceita qualquer requisição. O Postgres usa postgres/postgres no compose e no manifest do Kubernetes, este último com a senha em texto claro no YAML.

→ auth + rate limiting na API; senha do banco via Secret, como o secret.example.yaml já ensina para as outras variáveis

antes de produção

Uma conexão global com endpoints síncronos

pg() devolve sempre a mesma conexão, e os endpoints do FastAPI são def (não async def), então rodam num pool de threads. Várias requisições simultâneas compartilham o mesmo cursor de banco. Com um usuário só não dá problema, mas é o desenho que costuma falhar sob concorrência.

→ pool de conexões (psycopg_pool) em vez de uma conexão de módulo

de olho

O CI não reprova nada

ruff check . || true — o lint roda, mostra os problemas e sai com sucesso de qualquer jeito.

→ remova o || true quando o código estiver limpo

A UI ainda se apresenta como starter

Título da aba "assistant-ui Starter App" e um breadcrumb no cabeçalho que linka para a documentação do assistant-ui.

→ metadata em ui/app/layout.tsx e o cabeçalho em ui/app/assistant.tsx
